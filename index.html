Automated Weekly Threat Intelligence Pipeline

Objective: Built a fully automated scheduled pipeline that fetches, triages, and operationalizes fresh threat intelligence reports weekly — producing structured Sigma rules and hunt hypotheses with zero manual analyst input per cycle and a mandatory human-review gate before any output reaches the main branch.

Tools & Tech: Claude AI (scheduled cloud routine), Sigma, KQL, MITRE ATT&CK, GitHub (branch + draft PR governance), Python

Pipeline Design:

  • Sources Layer: 38 curated TI outlets — 35 global vendors/DFIR shops plus 3 MENA-dedicated sources (CTM360, Resecurity, Help AG) — checked weekly against a strict 7-day publication window; stale reports are excluded unconditionally.
  • MENA-Region Prioritization: Up to 5 reports processed per cycle, ranked by relevance to the MENA region — aligning pipeline output with the operational focus of the KSA financial and critical-infrastructure environment.
  • 4-Stage Cascade (fully automated): threat-intel-analyst (TTP/IOC/confidence extraction → structured JSON) → decision-agent (routes each TTP: detection candidate vs. hunt candidate, based on observability and FP manageability) → detection-engineer + threat-hunter in parallel (Sigma/KQL rules + structured hunt hypotheses).
  • Output Governance: Every run commits to a weekly/[date] branch and opens a draft PR — never pushes to main directly, never auto-merges. Empty weeks produce no PR. The exact routine prompt is version-controlled in WEEKLY-ROUTINE-PROMPT.md, making pipeline behavior fully auditable without touching any API config.

Proof-of-Concept Case — APT34/OilRig:

  • Manually exercised against Check Point Research's Veaty/Spearal/CacheHttp.dll report (APT34/OilRig targeting Iraqi government infrastructure, 2024-09-11): 18 TTPs extracted at medium confidence → 6 detection candidates produced (5 built as Sigma rules; 1 correctly declined because the candidate was a decaying IOC unsuitable for a durable rule) + 11 hunt hypotheses generated and honestly staged as inconclusive/continue-hunting with no live telemetry to query against.
  • Test run surfaced a gap in the scheduled routine (no regional weighting, no strict date window) that was corrected via PR #3 before automation went live.

Hunt-to-Detection Closure Loop

Objective: Built a structured three-agent workflow that prevents threat-hunting findings from dead-ending as one-off write-ups — routing threat-hunter JSON output through a gate-check into detection-engineer, then validating the resulting rule with purple-team-advisor before closing the loop.

Tools & Tech: Claude AI agents (threat-hunter, detection-engineer, purple-team-advisor), Sigma, KQL, MITRE ATT&CK, Atomic Red Team / MITRE CALDERA

Workflow:

  • Gate-check routing: Inspects threat-hunter's recommended_next_step field — only findings marked handoff_to_detection_engineering continue; continue_hunting routes back to threat-hunter; escalate_to_ir triggers the Major Incident Response Chain (active compromise, not a detection gap).
  • Detection Engineering (Step 2): detection-engineer receives the hunt's ttps, data_sources, and query_or_method fields — already in the shape it accepts from the CTI Triage Pipeline, no reformatting needed. Produces a Sigma/KQL rule, or an explicit visibility-gap flag if the behavior isn't yet observable (an unfireable rule is worse than an honest gap).
  • Validation (Step 3): purple-team-advisor simulates the exact technique using Atomic Red Team or equivalent in a non-production environment and confirms the SIEM/EDR actually alerts — "we built a rule" is not the same as "we confirmed it fires."
  • Failure Handling (Step 4): Distinguishes a logic gap (rule logic is wrong — detection-engineer fixes and re-tests once) from a pipeline/ingestion gap (log source or delay issue — document and close; looping detection-engineer against a problem one level below where it operates only creates false closure).
  • Closure Notification (Step 5): Logs validated status back to threat-hunter so the next hunt cycle deprioritizes re-hunting the same TTP and redirects effort to the next visibility gap.

Threat Hunting Queries & MITRE ATT&CK Detection Library

Objective: Developed and operationalized a library of threat-hunting queries and detection rules mapped to MITRE ATT&CK tactics and techniques, enabling proactive APT detection across enterprise environments.

Tools Used: IBM QRadar, Splunk, Elastic Stack (ELK), CrowdStrike, Sigma, MITRE ATT&CK Navigator

Methodology:

  • "Know Normal to Hunt Evil" Baseline (SANS FOR508): Built per-process baselines covering expected parent/path/account/instance-count/start-time for core OS processes (lsass, svchost, explorer, winlogon, etc.) — deviations from baseline (wrong parent, misspelled name, wrong path) surface masquerading malware and process injection attempts without relying on signature matching.
  • Three-Tier Hypothesis Framework: Structured hunt missions across three tiers — intelligence-led (actor TTP reports drive the hypothesis), TTP-driven (ATT&CK technique selected, hunt designs the data query), and anomaly-based (statistical deviation from established behavioral baseline). Each hunt produces a structured JSON output with hypothesis, ttps, data_sources, query_or_method, result, findings, and recommended_next_step.
  • ATT&CK Coverage Gap Analysis: Used MITRE ATT&CK Navigator to map existing detection rules against the full technique matrix, identifying blind spots by tactic — prioritizing coverage expansion in Initial Access, Lateral Movement, and Credential Access where APT dwell time is highest.
  • ATT&CK-Mapped Query Development: Created custom Sigma rules and SIEM correlation queries targeting high-value techniques: Kerberoasting (T1558.003), DCSync (T1003.006), Pass-the-Hash (T1550.002), WMI persistence (T1047), Golden Ticket (T1558.001), scheduled task abuse (T1053.005), PowerShell execution (T1059.001), and lateral movement via PsExec/Scheduled Tasks/WMI.
  • Telemetry Correlation: Correlated Windows event logs (4624/4625/4648/4698/4702/4768/4769), Sysmon (Event IDs 1/3/7/8/10/11/13), EDR telemetry, and network flow data — building multi-source detection logic that degrades gracefully when individual log sources are unavailable.
  • Hunt-to-Detection Handoff: Formalized findings routing — hunt output classified as finding + handoff_to_detection_engineering triggers structured handoff to detection engineering; escalate_to_ir routes directly to incident response; continue_hunting returns to the hunt queue without generating noise.
  • Detection Tuning: Iteratively refined rules against production telemetry to reduce false positives while broadening detection coverage — scoring each candidate on Coverage, Durability, Complexity, Confidence, FP rate, and Actionable content before promoting to production.

SOC Automation & Incident Response Playbooks

Objective: Built automated incident-response workflows and a structured multi-phase IR chain aligned to NIST SP 800-61 and SANS PICERL, standardizing detection through closure — including mandatory post-incident detection validation to confirm exposed gaps are actually fixed before an incident is closed.

Tools Used: IBM Resilient SOAR, Python, Bash, QRadar, MITRE ATT&CK

Methodology:

  • Classification-First Approach: All incidents are classified (P1–P4) before any downstream action is triggered — severity drives SITREP cadence, escalation path, and whether the full chain is warranted. A P4/informational finding exits the chain at Step 1; never runs downstream agents against noise.
  • Multi-Phase IR Chain (NIST SP 800-61 + SANS PICERL aligned): IR Coordinator (classify, open SITREP) → parallel DFIR forensics + artifact analysis (timeline, root cause, persistence/lateral-movement path) → SOC leadership escalation (confirm/upgrade severity, executive bridge decision) → BC/DR activation (conditional — only on critical system down, backups targeted, or ransomware confirmed) → IR Coordinator PIR (root cause, timeline, remediation, lessons learned) → purple-team validation → executive reporting.
  • Mandatory Detection Validation Step: purple-team-advisor runs the confirmed TTPs from forensic findings through its simulate-and-validate methodology before the incident is closed — testing whether existing detections would have caught the technique, or confirming new rules built in response to the gap actually fire. This step is not skippable under closure pressure: an incident that closes without confirming the detection gap is fixed is a recurrence waiting to happen.
  • Playbook Development: Created IR playbooks for phishing, ransomware, lateral movement, and identity compromise — each mapped to MITRE ATT&CK tactics/techniques with explicit containment actions, evidence-collection checklists, and SOAR-triggerable decision points.
  • SOAR Integration: Automated alert triage, IOC enrichment, and containment actions using IBM Resilient SOAR — reducing manual analyst steps and accelerating MTTR.
  • Python Scripting: Developed scripts for log parsing, IOC extraction, and ticket generation to eliminate redundant SOC workflows and feed structured data back into the detection feedback loop.

Comprehensive Vulnerability Assessment

Objective: Conducted a vulnerability assessment on local and external-facing assets to identify and mitigate security risks, leveraging both passive and active reconnaissance techniques.

Tools Used: Shodan, Nmap, Dirsearch, Sublist3r, Xray, Metasploit

Methodology:

  • Passive Information Gathering with Shodan: Used Shodan to perform passive reconnaissance, identifying publicly exposed services, devices, and their associated metadata. Collected information on open ports, service banners, and potential vulnerabilities for external-facing assets.
  • Active Information Gathering with Nmap: Conducted network scans using Nmap to enumerate open ports, running services, and operating system information. Used Nmap Scripting Engine (NSE) to detect vulnerabilities such as outdated software versions, default credentials, and misconfigurations.
  • Subdomain Enumeration: Used Sublist3r to discover additional subdomains, expanding the attack surface for potential vulnerabilities.
  • Directory Scanning with Dirsearch: Performed directory brute-forcing on web servers to locate hidden or sensitive directories, including admin panels and backup files.
  • Vulnerability Scanning with Xray: Utilized Xray scanner to identify critical vulnerabilities in web applications, including SQL injection, Cross-Site Scripting (XSS), and file inclusion vulnerabilities.
  • Exploitation and Post-Exploitation with Metasploit: Leveraged Metasploit Framework to simulate exploitation of identified vulnerabilities in a controlled environment, including privilege escalation and lateral movement.

Outcome:

  • Successfully uncovered 8 critical vulnerabilities, including exposed sensitive directories, SQL injection, XSS, and file upload vulnerabilities in web applications.
  • Provided a detailed report with prioritized mitigation strategies, recommending actions such as patch management, access control updates, and enhanced monitoring.
  • Strengthened the security posture of the organization by resolving all critical issues and improving overall resilience against potential attacks.
